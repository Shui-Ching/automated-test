# 自動派工機制可行性報告（Phase 4.4）

產生時間：2026-09-01　驗證環境：W 機（Windows）／`rtk proxy npx playwright test`

## 1. 目的與方法

驗證「測試失敗 → 依 `tests/contract/ac-coverage.json` 自動歸類負責單位（前端／後端／需人工設計審查）→ 產出派工單」這條鏈路是否可信賴。

因為目前沒有真人 QA 產出的獨立人工測試結果可比對，改用**刻意植入已知 bug**取代 PM 人工結果：植入前先判定「這個 bug 屬於哪個負責單位、預期哪些 AC 會轉紅」，等同人工測試的判斷基準；再實際跑自動化測試，比對自動化的判讀是否與人工判斷一致。四格定義：

| | 自動化：綠 | 自動化：紅 |
| :--- | :--- | :--- |
| **人工判斷：正常** | 真陰性（正常） | **假紅燈**：沒有 bug 卻被標成失敗 |
| **人工判斷：有 bug** | **假綠燈**：有 bug 卻被判斷成通過（最危險，代表測試漏抓） | 真陽性（正確抓到） |

## 2. 基準線

修正前先跑一次全量測試確認乾淨基準：**68 條全綠**，`test-results/dispatch.md` 顯示「沒有需要派工的失敗項目」。模擬資料乾淨、無已知缺陷，人工判斷同樣預期全數正常——這 68 條落在「真陰性」格。

## 4. 過程中發現並已修正的缺陷

**`tests/contract/contract-check.spec.ts` 契約檢查只掃描 `testid-map.json` 每個頁面的 `testids`，沒有掃描 `block_testids`（重複型 testid，例如 `pub-detail-block`、`page-form-block-group`）。** 因此「圖文區塊容器」這類會重複出現的 testid 改名或漏刻，契約檢查會誤判為綠燈放行，實際上該頁面的契約已經對不齊。上表實驗 4 第一次跑的結果就是這個缺陷的直接後果：本來該由契約檢查攔下的問題，變成功能測試轉紅、又被派工規則誤判成「需人工設計審查」——如果照單全收，會把一個「前端 testid 打錯字」的問題錯發給設計端審查。

已在本次修正 `contract-check.spec.ts`，補上對 `block_testids`（排除純說明用的 `note` 鍵）逐一斷言「至少出現一次」（`toHaveCount` 要求精確數量，重複型 testid 數量隨資料筆數而動，故用 `count() > 0`）。修正後重新執行同一個植入（testid 改名），契約檢查正確轉紅並標記「前端（契約不符，非 bug）」，正確排在下游那兩條功能測試失敗之上——依 `docs/project-plan.md` 第 267～278 行的既有判讀規則，人工看到契約紅燈時應先處理前端契約問題，暫緩另外兩條的「需人工設計審查」歸類（這兩條在契約修好前仍會顯示為失敗，是契約漂移的下游症狀，不是獨立的第二個 bug）。

## 5. 結論

本次抽樣（3 類負責單位規則各驗證 1 個真實 bug、外加 1 種契約漂移情境）觀察到的假綠燈為 **0 條**；假紅燈原本有 1 種情境會被誤判（實驗 4），根因是契約檢查的涵蓋缺口，已修正並重新驗證通過。

**這個結論只到「抽樣通過」，不是「窮舉證明」**：60 條 AC 裡目前只實際植入驗證了 8 條的失敗路徑（後端 2、前端 2、需人工設計審查 2、契約漂移相關 2），其餘 AC（例如 Toast 顯示、分頁行為、逾時、資料不存在等其他前端／後端情境）沿用既有的靜態分類規則，沒有另外做植入驗證——這些是「規則本身合理、但沒有實測」的部分，若要更高把握度，下次應輪流對這些類型各挑 1～2 條做同樣的植入驗證。

**更根本的限制：這套「植入已知 bug」的驗證方法，本質上只能證明真陽性，證明不了假綠燈為 0。** 植入實驗的做法是先看測試斷言了什麼，才決定要改壞程式碼的哪一行——這代表植入的 bug 一定落在「測試本來就有覆蓋」的路徑上，方法上不可能找到「測試完全沒覆蓋到、所以永遠不會轉紅」的那種 bug。真正會漏掉的假綠燈，來自根本沒有測試覆蓋的 AC，而不是測試覆蓋了但斷言寫錯的 AC。`tests/contract/ac-coverage.json` 裡目前有兩筆這種情況：id 20（`[PAG-ADM-FN-002] AC-B1 區塊版型每一組皆不可為空`）與 id 39（同規則於 `PAG-ADM-FN-003`），`test_file`／`test_title` 皆為 `null`，備註說明是「該規則的觸發條件在真實 UI 操作路徑下無法達成，只能用 `page.evaluate` 竄改內部狀態才測得到，判斷不值得寫成自動化測試」。這兩筆是目前已知、永久存在的假綠燈名額：如果這條防禦性檢核未來真的失效，自動化測試不會發現，只有人工測試才會。因此本報告的「假綠燈 0 條」要理解成「在已植入驗證的 8 條路徑裡是 0 條」，不是對全部 60 條 AC 的保證。

## 6. 對 Phase 4.5（抽成 skill）的建議

把這套「植入已知 bug → 跑測試 → 比對 `dispatch.md` 歸類是否符合預期」的流程本身固定下來會很有價值，之後每次新增 AC 或改動 `ac-coverage.json` 分類規則時，都可以重跑同一組已驗證過的植入案例當回歸測試，而不必每次重新手動想一輪測資。
