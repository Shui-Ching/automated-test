# 給 PM 的規格回饋清單

來源：`srs/` 底下六份功能規格與 `3.2_非功能需求.md`，逐條 AC 清點後整理。
本檔只列問題與建議，不動 `srs/` 任何檔案。修不修、怎麼修由 PM 決定。

依「不修就做不下去」的程度排序。

---

## A 級 — 不修就無法實作，會卡住下游

### A-1 前台列表的次要排序沒有可用的欄位（連鎖影響 5 條 AC）

**問題**
`[PUB-WEB-FN-001]` 的〈預設排序定義〉寫：「建立日期（由新至舊）；**同一建立日期時，以資料新增順序由新至舊為次要排序**。」

但 `[PAG-ADM-FN-002]` 特殊規則 5 明確寫：「建立日期由使用者自行指定，**不由系統自動帶入寫入時間**；可選取過去日期。」

而全部六份規格的〈欄位定義〉表裡，**沒有任何一個系統自動產生的識別欄位或寫入時間欄位**。也就是說「資料新增順序」這件事，系統根本沒有地方記錄，這條排序規則寫得出來但算不出來。

**連鎖影響**
`[PUB-WEB-FN-002]` 特殊規則 3 寫「上下則之排序基準與 PUB-WEB-FN-001 之〈預設排序定義〉完全一致」，所以 AC-P5、AC-P6、AC-P7、AC-P9 這四條上下則導覽的驗收，全部繼承同一個洞。加上 PUB-001 AC-P1 本身，共 5 條 AC 目前無法穩定驗收——同日期的兩筆資料誰在前面，會變成看實作心情。

**修法（三個選項，建議 A）**

先講一個關鍵前提：**主鍵其實已經隱含存在於規格中，只是從來沒被定義過，也沒說可以拿來排序。**
- `[PAG-ADM-FN-001]`〈按鈕與動作〉：「編輯：⋯⋯並隨附**主鍵**資訊」
- `[PUB-WEB-FN-001]`〈按鈕與動作〉：「點擊導向⋯⋯並隨附**主鍵**資訊」
- `[PUB-WEB-FN-002]` 基本流程 2：「系統依**主鍵**讀取該筆資料」

三份規格都在用它，但沒有任何一份的〈欄位定義〉表把它列出來。所以修法不是「加一個新欄位」，而是「把已經在用的東西寫進定義，並宣告它遞增」。

| 方案 | 做法 | 評估 |
| :--- | :--- | :--- |
| **A（建議）** | 在資料欄位定義補列主鍵：系統自動產生、遞增、使用者不可編輯、不顯示於畫面。PUB-001〈預設排序定義〉改為「建立日期（由新至舊）；同一建立日期時，以**主鍵由大至小**為次要排序」 | 改動最小，且把三份規格已經在用的欄位補上定義，順便修掉另一個文件缺口。實作與測試都能穩定驗證 |
| B | 次要排序改用「頁面名稱升冪」 | 不需要動欄位定義，但排序結果對使用者不直觀（同日期的資料會依筆劃／編碼順序跳動），且頁面名稱雖是唯一值，中文字排序在不同瀏覽器與資料庫的定序規則下結果可能不同，反而製造新的不確定性 |
| C | 拿掉次要排序，改成「同日期時順序不指定」 | **不可行**。PUB-002 的上下則導覽釘死在這個排序上，順序不指定等於 AC-P5／P6／P7／P9 沒有唯一正解，測試寫不出來 |

方案 A 對 PM 是兩處編輯：欄位定義表補一列、PUB-001 排序定義補半句話。

## B 級 — 功能有定義但沒有驗收條件，自動化測試會漏測

這三項不影響實作，但因為沒有 AC，測試腳本不會為它們產生任何測試案例——功能壞掉不會有人發現。

### B-1 「登出」沒有任何 AC

`[PAG-ADM-FN-001]`〈按鈕與動作〉定義了登出的行為（結束登入狀態、導回登入頁、Toast「已登出」），基本流程第 9 點也寫了，但 AC-P1～P5、AC-B1 沒有一條驗證它。

**建議**：補一條 AC，Then 至少要涵蓋「導回登入頁」與「登出後直接輸入後台網址仍被擋下」兩件事——只驗前者的話，登入狀態沒真的清掉也會通過。

### B-2 分頁功能完全沒有 AC

兩份列表（`PAG-ADM-FN-001`、`PUB-WEB-FN-001`）都定義了完整的分頁功能：每頁筆數可切換 10／20／50、顯示總筆數、跳頁輸入框、前後翻頁按鈕。

其中**只有「總筆數」被間接驗到**（PAG-001 AC-P1／P3／P5、PUB-001 AC-P3 的 Then 都提到總筆數）。**每頁筆數切換、跳頁輸入框、前後翻頁三項完全沒有 AC**，是一整塊有規格、零驗收的功能。

**建議**：補 2～3 條，例如「切換每頁 20 筆後列表顯示 20 筆」「跳至第 3 頁後序號從 21 起算」「位於第 1 頁時上一頁按鈕停用」。

### B-3 後台列表的預設排序沒有 AC

`[PAG-ADM-FN-001]` 定義了預設排序為「建立日期由新至舊」，但沒有對應 AC。前台列表有（PUB-001 AC-P1），後台沒有。

**建議**：比照 PUB-001 AC-P1 補一條。

## C 級 — 編號與引用錯誤，會讓 AC 追溯斷鏈

### C-1 NFR 編號整組差三號

`3.2_非功能需求.md` 只定義了 NFR-001～NFR-004，但六份功能檔引用的是 NFR-004／005／006／007：

| 功能檔引用 | 實際應為 | 內容 |
| :--- | :--- | :--- |
| NFR-004 | NFR-001 | 後台存取權限阻斷 |
| NFR-005 | NFR-002 | 登入逾時 |
| NFR-006 | NFR-003 | 前台免登入與後台入口隔離 |
| NFR-007 | NFR-004 | 資料寫入失敗處理 |

測試報告要回溯「這條 AC 對應哪條 NFR」時會全部指向不存在的編號。

### C-2 NFR-001 的「適用功能」把登入頁自己列進去了

NFR-001 是「後台所有頁面須具備登入狀態方可存取」，但適用功能欄第一個就是 `[AUT-ADM-FN-001]` 後台登入。照字面套用等於「登入頁要先登入才能開」。自動產生 AC↔NFR 對照時會生出一條自相矛盾的測試。

**建議**：把 `[AUT-ADM-FN-001]` 從 NFR-001 的適用範圍移除。

## D 級 — 影響自動化測試可行性，需要規格層決定

這三項不是規格寫錯，是規格寫法讓某些 AC 沒辦法自動驗證。要嘛調整規格，要嘛接受這幾條永遠只能人工測。

### D-1 NFR-002 的 30 分鐘逾時無法自動測

沒有任何自動化測試會等 30 分鐘。要自動驗這條，程式必須把逾時秒數做成可從測試注入的設定值（測試時設成 2 秒）。

**這是實作端的事，不需要改規格**，但 PM 要知道：驗收報告上這條的「已自動驗證」是用縮短後的秒數驗的，實際 30 分鐘這個數值本身仍需人工確認一次。

### D-2 NFR-004 的「資料寫入失敗」沒有觸發路徑

NFR-004 要求寫入失敗時中止作業、提示「系統忙碌中，請稍後再試」、保留已輸入內容、不留半筆資料。但在目前的模擬資料版本，寫入不會自己失敗，這條沒辦法自動觸發。

同 D-1，解法是在資料層留一個可注入的失敗開關。一樣需要 PM 知道這條的驗證方式跟其他 AC 不同。

### D-3 所有規格的 UI 截圖都是「待補」

六份規格的〈UI 介面〉全部寫 `![UI 截圖](待補：對應原型截圖路徑)`。

**這件事直接影響這次自動化驗收試作的核心目標。** 我們想做的是「測試失敗時自動判斷是設計、前端還是後端的問題」。但版型類的 AC（例如 PUB-002 AC-P1「圖片在左、文字在右」）如果沒有設計稿當比對基準，測試只能驗證「跟規格文字描述不符」，**無法區分是前端做錯了、還是規格本身寫錯了**。

換句話說，沒有截圖的話，三方派工實際上只能做到「後端／前端」兩方，加上一個「需人工設計審查」的標記，而不是真正的三方自動分派。

**建議**：至少為含版型的三份規格（PAG-002、PAG-003、PUB-002）補上原型截圖。

## E 級 — 工程便利性，非規格正確性問題

### E-1 規格檔名含中括號與空白

`[PAG-ADM-FN-001] 後台 頁面列表.md` 這種檔名，在 glob pattern 裡 `[...]` 是字元集語法、在 shell 裡空白要跳脫。之後要寫腳本把 AC 從規格自動抽出來對照測試結果時，這會是第一個踩到的坑。

**建議**：改成 `PAG-ADM-FN-001_後台_頁面列表.md`，中文保留，只拿掉中括號與空白。資料夾維持現狀。

### E-2 頁面內容以 HTML 原樣渲染是規格層的資安缺口

`[PAG-ADM-FN-002]` 特殊規則 4：「頁面內容以 HTML 格式儲存，**不套用一般字元集限制**」。
`[PUB-WEB-FN-002]` 欄位定義 C：「以後台儲存之 HTML **原樣渲染**」。

照字面實作就是把使用者輸入直接放進 `innerHTML`，等於在規格層開了一個 XSS 注入點。目前後台只有單一內建管理員帳號，風險有限；但這條規格若原封不動進到有多帳號的正式系統，任一個後台帳號被盜就能對所有前台訪客植入腳本。

**建議修法**：在 PUB-002 補一條特殊規則——渲染前做白名單消毒，允許標籤對齊編輯器工具列即可（粗體、斜體、項目清單、超連結、圖片），移除所有事件屬性與 `javascript:` 開頭的連結。AC-P4（粗體與清單要正常呈現）仍會通過。
